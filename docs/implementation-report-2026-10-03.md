# Implementation report: code that changes in place (Lattice 0.12.0 and 0.12.1, 2026-10-03)

A new built-in component, `code-morph`: the text of a code block changes from one position to the next, and the audience watches the old text turn into the new one. The motivating case is a bug fix (a line rewritten into another, into several, or several lines collapsing into one). The rules are in spec 8.11 (with 3.13, 8.6, 8.8, 8.9, 8.10, 10.4, 12 and 15); the rationale is report 3.14 and decision 21. The design was proposed and agreed before implementation (project doc `claude/v0.12-design.md`); Olivier's answers: `room=max` by default with `room=fit` on request, 600 ms, cumulative steps with a reserved `label` key, `mark` implemented but off by default, and a per-version `lang`.

## 1. What was built

- **Two authoring forms**, exclusive (LT021). `versions:` is read exactly as by `diff-steps` (the loader is now one helper, `read_versions` in `components/code.py`; the HTML of every `diff-steps` slide of the examples and the manual was compared with the 0.11.0 build and is identical), and a version may set its own `lang`. `file` with `steps:` writes the code once with segment markers; each step maps segment names to replacement text, cumulatively, `null` restoring the file's text. `label` and `lang` are reserved step keys. Replacements keep the indentation of the segment's first line (line-form segments include it), and an empty replacement of whole lines removes the lines. A replaced segment keeps its name and covers its new text; segments nested in it disappear while it is replaced (naming one is LT022, as is setting a segment and one nested in it in one step).
- **Units and alignment** (`components/morph.py`). Each version is highlighted with Pygments (`lexer_for`, Scheme correction included), tabs expanded to 8 columns, tokens cut at line ends and split into units (a word, or one other character); spaces are gaps, not units. Consecutive versions are aligned with `difflib`: lines first (on their units without spaces), equal lines and unique moved lines (at least six characters) pair in order, then the units of each changed region are aligned together, on class and text, or on text alone when the language changes. Surviving units keep one identity across versions. The data per unit is its position and class index per version (`null` when absent); text is in the HTML only.
- **Runtime** (`runtime/components/code-morph.js`, styles in `lattice.css`). Every unit is an absolutely positioned span at `--c` columns (`ch`) and `--r` rows (`1.5em`, rounded down to whole pixels where `round()` is supported, so rows land where lines of text do). `show` sets two custom properties per unit and a role class; CSS transitions do the motion in three phases (out 0 to 40 %, glide 20 to 80 %, in 60 to 100 % of `duration`). A non-animated show sets the same values with transitions off, so the end state cannot depend on the path. A show during a running change (skip keys, a quick second Right) switches to one 140 ms unphased glide from wherever the units are. `prefers-reduced-motion`, `duration=0`, preview and print place units directly. A transparent copy of the current text over the units carries selection and the segments. `room=max` keeps the tallest version's height; `room=fit` animates the height. Line numbers count the rows of the current version and do not move. `mark=true` tints arrivals with `--lt-add-bg` (no new theme token).
- **Arrows.** The morph dispatches `lt-relayout` (spec 10.4) after every show, with the timing of its glide; `arrow.js` handles it in a microtask (after every show of the step, so a follower arrow's own step is the one measured) and glides from what is on screen, with the morph's timing. The build-time arrow check (LT046) now counts component anchors, so an arrow at a segment that only exists in a later version is not warned about.
- **Diagnostics.** LT059 (warning): two consecutive versions identical. LT060 (warning): a character that is not one column of a monospace font (wide, combining, control).
- **Cache fixes found on the way** (spec 8.6, changelog row): a cached render result lost its `anchors`, so LT058 was not checked on cached builds since 0.11.0, and lost the warnings its render emitted (LT046 included). Both are now stored with the entry and the warnings reported again. `RenderContext.warn` takes an optional code for built-in components.

## 2. Decisions and why

- **Units on a grid, no measuring.** Code is monospace, so a position is two integers known at build time. The browser never diffs and never measures the code (arrows still measure their targets, as before).
- **CSS transitions rather than a `requestAnimationFrame` loop** (the trees use one): transitions continue from the current visual state when interrupted and need no bookkeeping, and the final state is the inline values a direct show writes.
- **Hidden units keep their last position.** They are invisible and the stage clips (`overflow: clip`), so they never add scrolling; the browser test compares the positions of visible units only.
- **`room=max` by default**, as agreed, so nothing else on the slide moves; the layout test then sees the block at its full height at every step.
- **Default labels**: as `diff-steps`, except that in a block whose versions do not all share one language every unlabelled version is named after its lexer (`Python`, `Scheme`).

## 6. Addendum, 0.12.1: tall code blocks scroll to their highlight, on screen and in the PDF

Noticed while writing the morph's scrolling, then confirmed and reported before fixing.

- **The bug.** `code.js` scrolled a `code` or `code-steps` block taller than its space with `line.offsetTop - clientHeight / 3`. The `offsetParent` of a line is the slide (`.lt-slide` is the first positioned ancestor), so the target was too large by the block's distance from the top of the slide. Measured on an 80-line file under a title and a paragraph: the highlighted line landed 76 px above the visible top instead of 144 px below it, at 3 of 4 steps, at every window size. In the examples and the manual, one slide was hit: the manual's "Extending Lattice: a plugin file", whose steps 1 and 2 showed dimmed code only.
- **A second bug.** The PDF copies each slide with `cloneNode`, which does not keep scroll positions, so a scrolled block printed from its top (the plugin slide's last step printed without its highlighted lines). `code-morph` had the same problem.
- **Fixes.** `code.js` measures the line against the block itself (bounding boxes divided by the slide scale, plus `scrollTop`), as `code-morph.js` does, and scrolls smoothly only on an animated step, at once otherwise (print and preview included). `snapshot` in `lattice.js` notes the scroll positions of the slide's elements while the copy still has the original's structure, and `print` restores them once the copy is in the document. Spec 8.8 now states the scrolling, 11.5 that copies keep scroll positions; changelog row 0.12.1.
- **Verification.** New Chromium test `test_scrolled_code_shows_its_highlight_on_screen_and_in_print` (single steps, a jump, a reload, print copies, and a long `code-morph` whose change is near the end); it fails with either old file and passes with the fixes. 180 passed. Looked at: the plugin slide at each step, and a real `lattice pdf --steps all` of the test deck (every page shows its highlighted line a third of the way down).
