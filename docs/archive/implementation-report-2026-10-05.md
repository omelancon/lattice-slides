# Implementation report: arrows at list items and bullets (Lattice 0.16.0, 2026-10-05)

An `arrow` end can now name an item of a list, `facts[2]`, and sit at the item's marker, `from_anchor=bullet` (or `to_anchor=bullet`). Both are checked at build time. The rules are in spec 8.8, 8.9 and 12 (with 15); the rationale is report section 3 (after named segments) and decision 25. The design was proposed and agreed before implementation (project doc `claude/v0.16-design.md`, with Olivier's answers).

## 1. What was found first

- An arrow could point at a bullet only through a selector (`#facts > li:nth-child(1)`), which the build cannot check, and the `left` side of a two-line item is the middle of the whole item, not its bullet (a 0.11.0 todo item).
- A list marker (`::marker`) has no box in the page: neither `getBoundingClientRect` nor `getComputedStyle` gives its position. Measured in Chromium (three fonts, 20, 28 and 40 px), the browser's disc sits 0.95em, 0.85em and 0.78em left of the text: not proportional to the font size, and specific to the engine. Text markers behave differently: an outside text marker ends exactly where the item's content starts, and its width is how far the first character moves when the marker is set `inside`. That held to the pixel in Chromium and Firefox, for bullets, nested bullets and numbers ("10." included).
- The plan agreed with Olivier (option B) was to draw every marker with an absolutely positioned `li::before` and read its box with `getComputedStyle`. It works, but it overrides any author rule on lists: the manual's `checklist` plugin and example 04's `cs-frames` set `list-style: none` and draw their own `::before` markers, which the global rule would have replaced or broken. So the implemented variant keeps the browser's markers and makes the built-in bullets text (`list-style-type` strings) under `:where()`: same outcome (Lattice chooses the markers of every list, exactly measurable in both engines), with author rules still winning.

## 2. What was built

- **Item paths** (`components/visual.py`): `LIST[N]`, `LIST[-N]` and `LIST[N][M]...` in `to`, `from` and string steps (YAML body or attribute block). The component splits them into the list id and a path (`to_item`, `from_item` in the step data); an index of 0 is LT022. `arrow_targets` reports bare ids only (LT046, unchanged), and `arrow_ends` lists the ends written as items or anchored at a bullet.
- **The `bullet` anchor**: accepted by `_anchor`, kept as is by `anchor_value`; without `from`, `to_anchor=bullet` gives `angle` 180, as a side gives its direction.
- **LT063** (`render.py`): the slide's final HTML (component HTML included) is parsed once with the standard `html.parser` into a light outline (`HtmlOutline`: tags, children, elements by id), and each item end is resolved on it like the runtime does. Errors: no element with that id, an element that is not a `<ul>` or `<ol>`, an index out of range (also negative), no nested list to descend into, `bullet` on a whole list ("write facts[N]"), on another element, or on a CSS selector.
- **Runtime** (`runtime/components/arrow.js`): `find` resolves an item path (direct `li` children, negative from the end, the first nested list between levels). The box of an `li` is its own content, without its nested lists (a `Range` ending before the first nested list), for any `li`, selectors included. `markerBox` measures the marker of an item: content start of the `li`, the first character's box, and its shift when `list-style-position` is `inside` for the time of one measurement (restored at once, so nothing is painted or observed); a list without a marker gives a zero-width box at the content start. `endBox` turns a `bullet` end into the anchor `180` on that box, so the existing geometry (gap, fixed direction, the other end aiming at it, the glide between steps) applies unchanged.
- **Text bullets** (`lattice.css`): `:where(.lt-body) ul` gets `"\2022\2002"`, a list nested in a list `"\25E6\2002"` and deeper `"\25AA\2002"` (bullet, white bullet, small square, each with an en space). The en space was chosen against screenshots: with a no-break space the bullet sat 3 px closer to the text than the disc did. Ordered lists keep their numbers.
- **Docs**: spec 8.8 (arrow row), 8.9 (targets, the new "List items" and "Markers" paragraphs, `bullet` in anchors and in the default angle), 12 (LT063), 15 (0.16 row); README (arrow row, version); manual: a new slide "Arrows at bullets" after "Arrow anchors", whose targets now use `anchor-points[1]` instead of `:nth-child` selectors, and "Arrows that move" mentions item paths; design report (paragraph after named segments, roadmap v0.16, decision 25); SKILL.md (structure, highest code, tests table, a pitfall "Bullets are text markers"); todo. Version 0.16.0.

## 3. Verification

- `pytest -rs`: 234 passed, no skips, in Chromium (15 new tests). `test_segments.py`: the step data of item paths, negative and nested indices, the attribute-block form, the `bullet` default angle, each LT063 case (ten), LT022 for `[0]`, a raw `<li id>` taking `bullet`, no LT046 for an item path. `test_runtime.py::test_arrow_at_bullets`: for a bullet, a nested bullet and an ordered list's "10.", the arrow's tail sits 0 to 14 px left of the marker's accent pixels (found in a screenshot) and within 3 px of their vertical middle, leaving to the left; a list without markers; an item with a nested list measured on its own line; `[-2]` with a bullet head and no `from`. The test was checked to fail with the marker width forced to 0 and with nested lists left in the item's box, and passes in Firefox 142 as well (installed in the sandbox for this release).
- **Existing decks**: every example and the manual were built with 0.15 and with 0.16 and every slide holding a list compared at its last step in Chromium: the only differing pixels are in the 11 px column of the markers (the text never moved), apart from the two manual slides that changed on purpose. Plugin lists (`checklist`, `cs-frames`) are unchanged.
- **Looked at**: the manual's "Arrows at bullets" at each step and "Arrow anchors" (Chromium, and Firefox for the first), a reconstruction of Olivier's `index-of-min` slide (code on the left, two lists on the right, every step), and side-by-side crops of old and new bullets. `python scripts/build_examples.py` rebuilt every deck; `lattice check --strict` on the manual and `check_docs.py` pass.

## 4. Not verified, and left open

- The bullets' size depends on the body font (the build machine falls back to its system font); the nested `◦` is smaller than the old circle. See the todo.
- A list whose theme sets `disc`, `circle` or `square` markers is measured approximately (spec 8.9); a right-to-left list is not handled (`bullet` assumes the marker on the left).
- An ordered list that does not start at 1 cannot directly follow its `{#id}` line (CommonMark), which LT063 reports as a paragraph; noted in the todo.
- `docs/implementation-report-2026-10-04.md` is copied to `docs/archive/`; the copy left in `docs/` (and the 10-03 one) needs a `git rm`.
