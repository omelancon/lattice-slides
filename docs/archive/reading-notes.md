## 1. Lattice (docs/*.md, README, src/)

Facts that constrain the component:

- Pipeline: `Loader.load` → `BodyBuilder.build` → `resolve_graph` → `render_components` (compiles steps) → `check_steps` → `emit_html`. A component is a Python class registered with `@register(name)`, with `Options` (pydantic), `body` (`yaml`/`text`/`none`), an optional `runtime` JS file and `css` list, and `render(block, opts, ctx) -> RenderResult(html, data, positions, meta)`.
- Animated components return `positions > 1` plus `data`; the runtime registers `Lattice.component(name, {mount, show, enter, leave, destroy})`. `show(inst, position, info)` must render any absolute position in any order; `info.animate` is true only on single steps (spec 10.1, 10.2). Frame stores (spec 9.3) hold full states or keyframes plus deltas; `api.frames(store)` hides the difference.
- Existing traces (`anim.py`): `Trace` (generic, delta authoring, `transient` per-frame parts, `meta` per frame), `GraphTrace`, `ArrayTrace`, `TreeTrace`, `GridTrace`. `tree-anim` is the precedent for shapes that change: positions are computed per frame at build time (`graphs.tree_layouts`), stored in the frame as `pos`, in one shared box; the runtime glides nodes on single steps (`tree-anim.js`). Design decision 10: graphs keep one layout, trees move.
- `ctx.call("file.py:fn", ...)` imports the author's file and registers it as a dependency; extra block options become keyword arguments (`_extras`). `ctx.layout(graph)` gives Graphviz `dot` positions and edge splines (`graphs.layout`), with a NetworkX fallback.
- Followers: `code {follow=trace}` highlights `meta[i]["line"]` or `meta[i]["lines"]`; any component with the same position count can follow a leader (`ctx.leader` gives the leader's `RenderResult`, including `meta`). This is the mechanism to pair the animation with a static CFG panel or with pseudo-code.
- `Lattice.renderPanel(el, panel, keys)` renders scalars, lists and maps (used for `panel:` in all animations). Theme tokens: `--lt-ink`, `--lt-muted`, `--lt-accent`, `--lt-active`, `--lt-frontier`, `--lt-good`, `--lt-warn`, `--lt-edge`, `--lt-bg`, `--lt-wall`, `--lt-on-strong`, `--lt-accent-soft`, `--lt-frontier-soft`. Node/edge state classes already styled: `active`, `frontier`, `visited`, `done`, `path`, `dim`, `tree`, `error`.
- Print mode duplicates component ids per page and rewrites `url(#...)`/`href="#..."`; a runtime must reference its own ids only that way (SKILL.md pitfalls).
- Adding a built-in component (SKILL.md): class in `components/`, registration in `components/__init__.py`, runtime in `runtime/components/`, styles in `lattice.css`, row in spec 8.8 and in the README table, a test, and an example so `test_layout.py` covers it. Diagnostics: next free code is LT054. Version bump: minor for features (0.4.0), and the version appears in README, spec, report, `__init__.py`, `pyproject.toml` (`check_docs.py` enforces this).
- Writing rule for all prose in the repository: no em dashes.
- `examples/04-custom-components` shows the plugin pattern (`lattice_plugins.py`, absolute `runtime` and `css` paths) if the component is not built in.

## 2. Thesis (docs/this_phase/thesis.pdf), chapters 1 to 3

Read in full: introduction, chapter 1 (background), chapter 2 (SBBV), chapter 3 (ΛV), sections 3.7 and 3.8, and the appendix titles. The evaluation sections and the two appended papers were skimmed only.

What the component must be able to show:

- **Abstract interpretation vocabulary** (1.1): contexts map variables to abstract types; union (with widening) at join points, narrowing at conditionals. Type lattice of figure 3: `fx`, `bg`, `fl`, `ot`, unions written `fx|fl`, complements written `!fx`, plus `⊤` and `⊥`.
- **BBV family** (1.3): EBBV (AOT, no union, version limit then generic version), LBBV (JIT, stubs; figure 5 shows `fact` with blocks A.1, B.1, B.2, C.1 ... and stubs). SBBV and ΛV are the AOT variants of this thesis.
- **SBBV** (chapter 2): the specialized CFG is built by a breadth-first traversal over *versions* (block + context). Data structures of figure 7: `block.allVersions` (includes merged), `block.reachableVersions`, `version.{block, context, body, merged, contextAfter}`. Algorithms 1.1 to 1.7: main loop (dequeue; skip unreachable or done; `mergeSome` when `|reachableVersions| > limit`; `specialize` if still reachable), `getOrCreateVersion`, `getVersion` (follows the `merged` chain), `specialize` (instruction by instruction, stop after a halting instruction), `specializeGoto` (filter context to target parameters), `specializeIf` (narrow both sides; ⊥ on one side turns the `if` into a `goto`), `mergeSome` (heuristic picks versions; new version for the union with widening; the merged ones point to it). Merges remove edges, so a single-source dynamic reachability structure is needed (Even-Shiloach tree in the real implementation; small graphs can simply recompute). Post-processing removes jump cascades.
- **Merge heuristics** (2.2.3, 3.4, appendix A): "similarity" (Hamming distance per variable plus a specificity bias; separable and therefore poor at keeping monomorphic contexts, figure 8), "arithmetic" (merge contexts containing a possible bignum first, keep pure fx or fl contexts apart, Hamming as tiebreaker), "random". Algorithm 2.11: any local heuristic is a distance function over pairs.
- **Worked SBBV example**: `find` (2.1.1, figure 6): source blocks A to M with redundant `pair?` checks; the specialized CFG has `A1` (generic entry) and `A2` (`p: proc` loop entry), the hot loop `A2 → F → A2` has no `procedure?` check, unreachable `pair?` tests disappear. Entry points are starred.
- **ΛV** (chapter 3): functions become *hyperfunctions* with several entry points, each listing the indexed return points `K:(...)` it needs; `K[i]` invokes return point `i`. Representation: CPS after lambda-lifting, one lambda per block with all live variables as parameters, `call f.entry  ctx→ctx: K[i] ...  args`, non-tail calls pass `(lambda (r) (B K n r))` as return points. Every hyperfunction has an implicit generic entry with one return point. Preprocessing (3.3.1): desugar, alpha-convert, assignment-convert, CPS, lambda-lift; the top level is wrapped into `$top-level`.
- **ΛV algorithm** (3.3.3, figure 17, algorithms 2.1 to 2.10): same loop as SBBV plus a forward component (`specializeCall`: when the callee is a single known hyperfunction, request an entry version for the argument context, mark it, record the call site, and for every exit site already reachable from that entry create a return point whose context is `callContext ∩ exitSite.contextAfter`) and a backward component (`specializeExit` marks an exit and notifies the entries it is reachable from; `addReturnPoints` / `removeReturnPoints` cascade through call sites; `mergeSome` redirects edges and fires both). Contexts also keep parameter types so exits can refine the caller's arguments. Multi-source reachability interface: `addEdge`, `removeEdge`, `redirectEdges`, `markExit`, `markEntry`, each returning entry/exit pairs that became (dis)connected. Generic entries of every hyperfunction are traversed too (the implementation enqueues them after the top-level traversal is done). An index allocation phase orders return points at the end.
- **Worked ΛV examples**: `square`/`power4` (figures 13 to 15: three return points `[0] fx`, `[1] fl`, `[2] fx|fl|bg`; entry `Z` only needs `[1]`; operators as hyperfunctions need equivalence classes `a/b` to check one type instead of two), `fact` (figure 16: two entries A1/A2, return points `[0]` fx and `[1]` generic, operator calls `=[X]`, `-[Y]`, `*[Y]` drawn as external nodes with `[i]` return edges).
- **Limitations** (3.7) worth keeping in mind for a faithful-enough model: callee must be uniquely known at a specialized call site; contexts track types only (no intervals in ΛV); the hyperfunction implementation is pure Scheme.

## 3. Lambda Versioning implementation (docs/this_phase/lambda-versioning)

Gambit Scheme, `src/main.scm` drives: read + minimal RTS → `normalize` → `cps-module` (blocks as `$MULTIFUNCTION` forms with `entries:`/`blocks:`/`K:`) → `lambda-versioning` (breadth-first, `merge?` before `walk`, `entry-points!` grows then shrinks return points after each step, generic entries of all multifunctions enqueued once the queue first empties, unused entry points cleaned up at the end) → `lambda-versioning->specialized-multifunctions` → `.lv.scm`. Flags of interest: `--version-limit`, `--rts-version-limit`, `--merge similarity|arithmetic|random`, `--traversal`, `--sbbv` (disables the interprocedural parts), `--partial N`, `--plot`, `--runtime-trace`.

- **Contexts** (`context/context.scm`): a typeset is a bitmap over `FX RATNUM BIGNUM FL TRUE FALSE NULL STRING CHAR SYMBOL VECTOR F64VECTOR PAIR BOX OTHER CONT` plus an optional constant and a set of known multifunction identities (`MULTIF id`, `ANYMULTIF`). Contexts also hold equivalence classes and the types of the hyperfunction's own arguments. Distance functions `context-distance-arithmetic*` and `context-distance-similarity*` are the ones described in the thesis.
- **Plot** (`plot/plot.scm`, `add-bbv-state-to-plot!`): after each `walk`, a *state* is recorded: reachable version nodes `{id, multifId, blockId, label}`, edges from the reachability graph, `kind` (`did-walk`, `will-merge`, `did-merge`), a message, a highlight list, time and memory. Per-version origin code, specialized code and pretty-printed context are added once at the end. The output is a vis-network page with navigation (`<<< < > >>>`), jump to next merge, a context panel and charts. `static/share/lvdemo.*.html` on the website are such outputs (2 to 14 MB). This gives a possible importer: the state stream is exactly the kind of frame sequence the Lattice component needs, minus layout.
- `py_visualization/`: a matplotlib/DOT CFG drawer for `$MULTIFUNCTION` forms (entries as ellipses, blocks as boxes, `K:i` return nodes as diamonds). Static only; useful as a reference for how a hyperfunction reads as a graph.

## 4. Blog post (docs/this_phase/my-page, "SBBV visualization tool")

`templates/blog/sbbv.html` + `static/module/blog/sbbv.js` (2031 lines) + `sbbv.css`. A self-contained SBBV in JavaScript on a toy register IR (`MOV`, `IS_INT`, `IS_FLO`, `IS_ARR`, `INT_ADD`, `FLO_ADD`, `ARR_LEN`, `ARR_GET`, `JUMP`, `JUMPIF`, `CALL $runtime ret`, `RETURN`, `ERROR`; types `int`, `float`, `array`, with `!int` and `int|float` notation). Ideas to keep:

- The algorithm is a generator that *yields visualization events*: `init`, `step` (dequeued and created, reachable again, queued), `mustMerge`, `willMerge`, `merged` (with unreachable-after-merge and reachable-again lists), `done`. A legend sentence is produced from each event; block labels in the legend are clickable and select the node.
- Two panels: the original CFG (static) and the specialized CFG; versions inherit the colour of their origin block; queued (in-progress) versions have dashed borders; highlighted versions get a thick coloured border (green for new, red for merge candidates); hovering shows the context.
- Layout: vis-network hierarchical `LR`, level = rank of the origin block in the source CFG (plus a manual `shiftLevel`), so versions of the same block line up. This is stable across steps and reads well; it is the layout idea the plan adopts (computed in Python instead).
- A "single block specialization" canvas shows one origin block, the context, and the specialized block with removed instructions struck through and a `jumpif` turned into a `goto`. This is the instruction-level view.
- The version limit is an input; changing it re-runs the algorithm (dry run to count steps). Back is implemented by re-running from the start, which Lattice's full-state frames make unnecessary.
- Merge heuristic used there: similarity plus specificity plus a "backward score" that prefers merging an unrolled iteration into the loop entry rather than two unrolled iterations of parallel loops.

## 5. Consequences for the plan

1. The natural Lattice shape is a new trace class producing one frame per algorithm event, computed by a Python implementation of SBBV and ΛV on a small IR, and a runtime that draws versions and edges from per-frame positions (tree-anim precedent), with origin colours, dashed queued versions, starred entries and indexed return edges (thesis figure style).
2. Positions per frame must come from a layout that keeps versions of the same origin block on the same row (blog idea), computed in Python once per frame, with gliding on single steps.
3. Pairing with other components should go through followers: a static source CFG that highlights the origin of the current step, and a `code` block showing the algorithm or the program.
4. An importer for the Gambit `--plot` state stream is possible later; the frame format should not preclude it.
