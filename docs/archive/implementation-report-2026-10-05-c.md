# Implementation report: highlights in `code-morph` (Lattice 0.18.0, 2026-10-05)

A `code-morph` now highlights lines and segments the way a `code` block does, per version or per step, with a default for every position and the keyword `changed` for the rows where new tokens arrived. The rules are in spec 8.8, 8.10 and 8.11 (with 15); the rationale is report section 3 (the paragraph on code that changes) and decision 27. The design was proposed and agreed before implementation (project doc `claude/v0.18-design.md`, with Olivier's answers). This is the third release of the day, hence the `-c` in the name.

## 1. What was found first

- `code-morph` had no `highlight`: not as an option, not in a version, not in a step, and a `code` follower of a morph highlights nothing (its `meta` holds no lines). `read_versions`, shared with `diff-steps`, ignored any unknown key of a version.
- The `code` CSS could not simply be reused. A morph has no `.lt-line` rows: every unit is placed on a grid. The text copy that holds the segments lies over the units with transparent text, for selection and arrows, so an opaque `--lt-hl-bg` there would hide the tokens. Units already use their opacity to fade in and out.

## 2. What was built

- **Options and syntax** (`components/morph.py`, `components/code.py`): `MorphOptions.highlight` (string, number or list), `highlight` in a version mapping (`read_versions` now returns it, with whether it was given) and `highlight` as a reserved key of a step (beside `label` and `lang`). A position's own value wins, even when empty (`""`, an empty list or null); otherwise the option applies. Not cumulative.
- **Resolution** (`resolve_highlights`): targets are parsed with `parse_targets` (lines, ranges, names) after taking out the keyword `changed`, which is `changed_rows`: the rows of the version holding a unit that is new there (none at position 0). Checks (LT022, through `ComponentError`): in a position's own targets, a line beyond its rows or a name that is not a segment there; in the default, a line beyond the rows of a position it applies to, or a name that is a segment at no position (where it is absent, it lights nothing); malformed targets.
- **Highlight layers** (`highlight_layer`): per position, one element per highlighted row (`lt-line lt-hl`) and per row holding a highlighted segment (`lt-line`), positioned with `--r`, text transparent, the lit segment pieces wrapped as `lt-seg lt-hl` without `id` or `data-lt-seg` (so arrows never measure them). The undimmed rows of each position go to the data as `hl` (null where nothing is highlighted), the layers as `under`. Without any highlight, neither the data keys nor the layer markup are emitted, and the block's HTML is byte for byte what it was.
- **Runtime** (`runtime/components/code-morph.js`): two slots (`.lt-morph-hl`) under the units; at each change of position the other slot takes the new layer and becomes current, so the old one fades out while the new one fades in. `place` marks the units and line numbers of undimmed rows `lt-mt-lit` and the box `lt-morph-dim` when the position highlights anything. `reveal` scrolls to the first lit row, or to the first changed row as before.
- **Styles** (`runtime/lattice.css`): layer rows take the `.lt-line` look (padding, border, `--lt-hl` and `--lt-hl-bg`) and the units' row transform; the stage fills the code box when highlights exist, so a band spans it as a code line does; dimming is `.lt-morph-dim .lt-mt:not(.lt-mt-lit):not(.lt-mt-off)` at 0.38 (line numbers 0.23, as a dimmed `.lt-ln`). Phases: the old slot fades out over the first 40 %, surviving units change opacity during the glide (20 to 80 %), the new slot fades in over the last 40 %, arriving units fade in to their dimmed or lit opacity; the quick and still modes as for the units. No new theme token.
- **`diff-steps`**: a `highlight` in one of its versions is LT022 ("a diff does not highlight").
- **Docs**: spec 8.8 (the `code-morph` and `diff-steps` rows), 8.10 (Highlights name `code-morph`), 8.11 (versions, reserved step keys, options, two "Highlights" paragraphs, Motion, scrolling), 15 (0.18 row); README (code-morph row, version); manual: a new live slide "Highlights in a morph" after "Morphing named segments" and a `highlight` row in "Code that changes"; example 05's bug fix uses `highlight=changed`; design report (paragraph on code that changes, roadmap v0.18, decision 27); SKILL.md (structure, tests table, pitfall "Morph highlights are painted under the units", report names `-b`, `-c`); todo; the 0.17.0 report copied to `docs/archive/`. Version 0.18.0.

## 3. Verification

- `pytest -rs`: 279 passed, no skips, in Chromium (12 new tests). `test_morph.py`: per-version targets and the default, a cleared position, the layers (bands, rows holding a segment, marks without ids or `data-lt-seg`, the dim class at position 0), steps not cumulative and `highlight` not read as a segment, `changed` alone and mixed, unchanged output without highlights, a default segment absent at some positions, each LT022 case, `diff-steps`. `test_runtime.py`: a highlighted morph added to the deck of `test_code_morph_runtime_renders_positions_alike`, whose geometry now includes the visible layer and the dim state, so the same highlights are checked after a fresh load, random jumps, animated steps both ways, an interrupted step and skip playback; the print copy of a highlighted position; and a new `test_code_morph_highlights_look_like_code` comparing a morph and a `code` block with the same `highlight` (band and segment mark within 1 px, since morph rows sit on whole pixels; border, band and underline pixels equal; the same dimmed opacity) and the scroll to a highlighted row of a long morph (line 40, not the changed line 70).
- **Existing decks**: every example and the manual rebuilt. The morph slides without highlights of the manual were compared on pixels with their 0.17.0 build at every step: identical, apart from the new table row of "Code that changes".
- **Looked at** (Chromium, 1280x720): the manual's "Highlights in a morph" at each step, example 05's bug fix at each step, frames in the middle of an animated step (the old band fading, then the new segment mark), and both forms in the dark theme. `lattice check --strict` on the manual and `check_docs.py` pass.

## 4. Not verified, and left open

- Only Chromium was used; the layers use the same absolute placement and transforms as the units, which Firefox handles (0.12.0), but the cross-fade was not watched there.
- At the last step of example 05, `changed` leaves `self.order.remove(key)` (a survivor of the old code) dimmed in the middle of the four highlighted rows: that is the agreed meaning of `changed`; see the todo.
- A `code` following a morph still highlights nothing (todo).
