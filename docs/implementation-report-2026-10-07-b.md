# Implementation report: paths through the versions (Lattice 0.28.0, 2026-10-07)

Once Static Basic Block Versioning is done, a talk wants to show what the specialized graph does for one kind of input: which versions a flonum goes through, and which tests are left on the way. `bbv-anim` had no way to highlight a set of versions; the defense deck's slide "SBBV: A first example" needed one (the flonum path of `polynomial`, with an arrow at the only `flonum?` test). The new option `paths` adds one frame per path after the run. The rules are in spec 9.5 (paragraph "Paths", the marks and edge states of "Frames") and 8.8 (the `bbv-anim` and `bbv-cfg` rows), with 15; the rationale is in design report 3.10 and decision 38. The design was reviewed by Olivier before the work (dimming on by default, both forms, a minor release).

## 1. What was built

- **Paths** (`bbv/trace.py`, `VersioningTrace._add_paths` and its helpers, called after the run and before `finalize`):
  - `input: {x: fl}`: the types are read with `Type.parse` (intervals dropped unless `intervals` is on); the walk starts at the entry version of the entry function and follows `goto`, `true` and `false` edges of the last frame, entering a version when its entry context meets every input type on the parameters (a may-reach set);
  - `versions: [A1, D1]`: the labels drawn in the last frame;
  - the frame copies the last frame's nodes and edges without marks and states, marks the path's versions `path` and its edges `path`, the others `dim` (unless `dim: false`), and keeps the panel; the automatic caption reads `PATH x: fl · A1 → D1 → E1 → J3 → M1 → N1 · 2 tests` (chips joined by `→` only when the path is one sequence; the count is the tests not removed on the path); `caption` replaces it;
  - meta `{"event": "path", "blocks": [...], "function": ..., "algo": []}`;
  - errors (as `ValueError`, reported by the component as LT022): `algorithm: lv`, `until`, neither or both forms, unknown keys, a non-parameter, an unreadable type, a label not drawn, an input the entry version does not admit, a `dim` that is not a boolean.
- **Component** (`components/bbv.py`): the `paths` option of `BbvAnimOptions` (and in `_KNOWN`, so it never reaches a program function); a following `bbv-cfg` turns a meta with `blocks` into a list of highlighted vids.
- **Runtime** (`bbv.js`): `path` and `dim` among the edge marker states, the `path` operation badge in the `good` tone, a follower highlight that may be a list (its blocks marked `path`). **CSS** (`lattice.css`): `mk-path` and `st-path` in `--lt-good` (the colour of `graph-anim`'s `path`), `mk-dim` and `st-dim` at 30 % opacity. A first version used the amber of `active`; the arrowheads came out green, because `.lt-arrow.st-path` already belongs to `graph-anim`, which settled the colour.
- **Docs**: spec (above); README (the `bbv-anim` row); `docs/USER_SKILL.md` (a "paths through the versions" row, the `bbv-cfg` row); `docs/SKILL.md` (the test table); design report (3.10, roadmap v0.28, decision 38); todo; the manual's options table, two new slides "Paths through the versions" (`bbv-paths`: the polynomial program, its source CFG following, two paths and an arrow) and "Writing a path" (`bbv-paths-syntax`), a mention in "Reading the drawing", and `user_manual/programs/polynomial.bbv`; the 0.27 report copied to `docs/archive/` and listed in its README (to `git rm` in `docs/`, see the todo); version 0.28.0.
